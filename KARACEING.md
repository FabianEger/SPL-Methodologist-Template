# KA-RaceIng case study in the Methodologist Template

This branch of the template implements the evolution scenarios of the KA-RaceIng product line
(`EvolutionScenarios/concrete_scenarios.tex`, 51 concrete instances) and the KA-RaceIng scenarios of the
*Inconsistency Scenarios* TechReport (R1–R10, see `REPORT_SCENARIOS.md`) on top of the existing
template. The existing brake-system demo (legacy CAD, brake system, its reactions and tests) is unchanged.

```
model/src/main/ecore         metamodels (+ genmodels), see "Metamodels"
consistency/.../karaceing    KA-RaceIng reactions (generated by karaceing-generator/rxgen.py)
  fcpr/<ROLE>/                 Feature CPRs per stakeholder role (copy of the existing pattern)
  fcpr/FeatureRemovalTo*       removed features -> artefacts
  reverse/*ToFeatureModel      new / removed artefacts -> feature model
  overlap/Overlap*To*          overlapping artefacts between domains (+ BOM, brake system, requirement traces)
  config/                      ConfigCPR for removed features
consistency/src/main/java/.../karaceing   KARaceIngUtil, KARaceIngOverlapRules (attribute-level overlap rules AR1-AR13)
vsum/src/main/java/.../karaceing          KARaceIngChangePropagationSpecifications (all CPS, generated)
vsum/src/test/resources/initialstate      initial state as a persisted VSUM: 13 models + vsum/ (models.models, uuid.uuid,
                                          correspondences.correspondence)
vsum/src/test/java/.../karaceing          InitialStateLoader, KARaceIngTestBase, InitialStateTest, Scenario1Test ... Scenario6Test,
                                          ReportScenarioTest (R1-R10)
docs/OVERLAP_CATALOGUE.md                 every overlap of the initial state with kind K1-K11, source and justification (generated)
karaceing-generator                       Python generators (metamodels, initial state, reactions)
```

## Build and run

```
./mvnw clean verify                                  # everything
./mvnw verify -pl vsum -am -Dtest='InitialStateTest,Scenario*Test,ReportScenarioTest' -Dsurefire.failIfNoSpecifiedTests=false
```

**Status (2026-10-26):** `./mvnw clean verify` succeeds: all modules build, 94 tests run, 0 failures,
16 skipped (scenarios 2 and 5, and R10, see below). This includes the existing brake / CAD / addition tests.

Provided metamodels:

* `UVL.ecore` and `configurationsMM.ecore` are used **exactly as provided** (not changed).
* `cad.ecore`: only the EClass `Object` is renamed to `DocumentObject` (`Object` clashes with
  `java.lang.Object` in the generated code). Java package `tools.vitruv.methodologisttemplate.model.cad`.
* The previous CAD metamodel (Namespace / Parameter, `http://www.example.org/cad`) is kept as
  `legacycad.ecore` with its old Java package, so the brake-system demo still builds.
* `sysML.ecore` is not used and not generated (see open questions).

Consequences of the unchanged UVL / configuration metamodels:

* Cross-tree constraints are **not** part of the feature model: the UVL metamodel has the classes
  (`Constraints`, `Constraint`, `Formula`, `BinaryConst`, `Predicate`, `Reference`, ...), but a
  `Reference` / `TermReference` cannot point to a `Feature`, `Constant` has no value, `Negation` /
  `ParenthesisConst` have no operand, and the operands of `BinaryConst` / `Predicate` (`connects`) are
  non-containment references, so nested formulas cannot be stored. Constraints will be added as
  VitruvOCL constraints; scenarios 2 and 5 (adding / removing constraints) are therefore documented
  as disabled tests.
* Typed features (`MaxVehicleMass`, ...) carry an `Integer` element in `Feature.attribute`.
  Abstract features and the values of typed features per car cannot be represented.
* Configurations have no name: EV3, CV2 and CV1 are configurations 0, 1, 2 of `karaceing.config`.

## Initial state

The design rationale of the initial state (which instances, how they are linked, why) is explained in
[INITIAL_STATE.md](INITIAL_STATE.md).

Generated by `karaceing-generator/initstate.py` from `SPL_FeatureModels_v2_Stakeholders`
(role models, requirement mappings, the three car configurations):

* `karaceing.uvl`: 259 features (root `KARaceIngSPL`, one Mandatory group per domain root as the
  pattern expects), feature tree only.
* `karaceing.config`: EV3, CV2, CV1 (configurations 0, 1, 2) with all decisions (open design choices
  completed with the example completion). All three were checked to be valid products against the
  113 constraints of the role models when the initial state was generated.
* Domain models: every feature of a role is realised by one element of the role's model (CAD:
  Assembly, leaf parts get a Box, typed features a Sketch with a named dimension; ELEC: Circuit
  with a Device for leaves; SIM: SubSystem with a Block; THERMO: ThermalSystem with an element by
  kind; VAL: TestSuite / TestCase; PRJ: Section with the PRJ requirements). Scenario-specific
  artefacts are added (lidar bracket, over-pressure relays, ROS1 nodes, old inverter, BSPD test,
  backfire analysis, CV1-chassis adapter, ...). 1,068 requirements of the survey are in the
  requirements specification.
* `vsum/` holds the VSUM metadata in the format Vitruvius writes itself (compare `vsumexample/vsum`):
  * `models.models`: the 13 model URIs;
  * `uuid.uuid`: a UUID for each of the 4,960 model elements (`UUID|<model URI>#/0/<path>`);
  * `correspondences.correspondence`: 3,599 `ReactionsCorrespondence`s with relative hrefs into the models:
    * tag `""`: feature <-> artefact. **Every artefact corresponds to a feature**: details and
      scenario artefacts get the feature of their containing element, requirements their mapped features,
      and BOM items and brake components the feature of the overlapping CAD element. The other links with
      this tag are UVL model <-> configuration model, feature <-> configuration feature, and UVL model <->
      `uvlPackage.Literals.UVL_MODEL` (as uvl2uvl does). See INITIAL_STATE.md, P6;
    * tag `"overlap"`: artefacts of different roles that overlap semantically (the 32 cross-role
      interface constraints of the composition plus the overlaps the scenarios need), CAD parts <-> BOM
      items, brake components <-> DES brake assembly;
    * tag `"requirement"`: requirement <-> artefact realising a feature the requirement is mapped to.

**Loading in the tests.** Every test class has a `@BeforeEach` method `loadInitialState(@TempDir Path)`
that calls `openInitialState(...)`: `InitialStateLoader` copies `src/test/resources/initialstate` into
the temporary folder of the test and creates the VSUM on it with `VirtualModelBuilder`
(`withStorageFolder(folder)...buildAndInitialize()`), which loads the models, the UUIDs and the
correspondences like any persisted VSUM. Vitruvius stores absolute file URIs in `models.models` and
`uuid.uuid`, so these two files contain the placeholder `file:/KARACEING_INITIAL_STATE`, which the loader
replaces by the URI of the temporary folder. No reaction runs while the initial state is opened.

## Reactions

**One CPS per metamodel pair.** Vitruvius accepts only one change propagation specification per
(source, target) metamodel pair (`VirtualModelBuilder` throws "already contains the change propagation
specification ... between"). Therefore the segments are combined per pair, exactly like
`CombinedUVLToCAD` combines `feature2cad` and `featureRoot2cad`:
`fcpr/FeatureCPRsTo<MM>` imports `featureTo<ROLE>` and `rootFeatureTo<ROLE>` of all roles with that
metamodel (Cad: DES, CRASH, KIN, AERO) and `featureRemovalTo<MM>`; `config/ConfigCPRsKARaceIng` imports the
template's `feature2config` and `featureEvolutionToConfig`. Only these combined segments, the reverse
and the overlap segments are registered (`KARaceIngChangePropagationSpecifications.all()`, 63 CPS);
`rxgen.py` checks that no pair occurs twice and that no segment names differ only in case.

**Feature CPRs (the pattern).** `fcpr/<ROLE>/RootFeatureTo<ROLE>` and `FeatureTo<ROLE>` are copies of
`UVL2CAD/RootFeatureToCAD` and `FeatureToCAD`. Unchanged: the trigger (`Feature inserted in Group[feature]` with
`FeatureTreeUtil.isFeatureAddedtoThisDomain`), the decision routine (skip if the feature already has
a correspondent in the metamodel, Existing / New dialog, look up the element of the parent feature,
branch on its class), `mapToExisting...` (choice among `EMFUtil.getAllContainedEObjects`) and the
create routines (choice among `EMFUtil.findContainedClasses`, one typed routine per class).
Parameterised per role: domain root name, metamodel, file name, the container classes
(CAD: CADDocument, Assembly; ELEC: ElectricalDesign, Circuit, Device; SIM: SimulinkModel, SubSystem;
THERMO: ThermalAnalysisModel, ThermalSystem; VAL: TestBenchConfiguration, TestSuite, TestCase;
PRJ: RequirementsSpecification, Section). Small additions: the dialog messages contain the feature
name (so that tests can answer them), created elements get the feature's name, and
`EMFUtil.getAllNamesOfEObjects` no longer fails on elements without a `name` attribute. Because every
artefact corresponds to a feature, a parent feature can be realised by several elements of one model. Where
the pattern stopped in that case ("Multiple corresponding EClasses"), it now takes the outermost element
(`KARaceIngUtil.outermost`), or asks if that is ambiguous. The create and map routines get this element as
a parameter instead of retrieving the container again. The
generated `case`s follow `EMFUtil.findContainedClasses` exactly (an abstract type stands for its concrete
subclasses, a concrete type only for itself), so every case matches a choice of the dialog.

Identifiers in generated reactions avoid the keywords of the Reactions language (e.g. `element`,
`val`, `names`, `root`, `check`, `created`; full list in `InternalReactionsLanguage.tokens`). A dialog
with only one possible answer is skipped in the new CPRs (Vitruvius needs at least two choices).

**Other CPRs (new).**
Rule for all of them: **there is no artefact without a feature.**
* `FeatureRemovalTo<MM>`: an artefact of a removed feature that still realises another feature keeps
  it. Otherwise it is deleted or kept and mapped to the parent feature.
* `<MM>ToFeatureModel` (also for BOM and brake system): every new artefact is mapped to the feature of
  its containing element, to the features of an element it overlaps with, to another existing feature,
  or to a new feature. A removed artefact loses its feature links, and a feature without any remaining
  realisation is removed or kept.
* `Overlap<Src>To<Tgt>`: a new element below an artefact with overlaps gets a counterpart in the
  other domain (created or linked) or the overlap is ignored; a removed artefact's counterparts are
  deleted or kept; requirement traces of removed elements are removed.
  Attribute level (since 2026-10-26): every attribute, reference and containment change of a source
  artefact (or of an element below it) is passed to `KARaceIngOverlapRules` together with the anchor (the
  nearest element with overlaps or traces in the target model) and its counterparts. The rules AR1–AR13
  write derived values (mass / material / specification of BOM items, mass / inertia / heat capacity /
  venting / wear / signal parameters of SIM blocks, material data of thermal components, mounting
  references, expected results and pass criteria of tests, part numbers) and notify the owner of every
  counterpart with a role-addressed message `[Notify → <role>] ...` (Vitruvius notification dialog) that
  explains origin (traced requirements), propagation path and contact. Values written by a rule do not
  cause echo notifications; one notification per role and state of the anchor. Removing an artefact
  reports the requirements no other artefact of that model realises any more (AR10). New counterparts are
  initialised (AR13). See `REPORT_SCENARIOS.md` and `docs/OVERLAP_CATALOGUE.md`.
* Requirement traces: a requirement traces to every artefact of the features it is mapped to. The
  reverse FCPRs keep this: a newly mapped artefact gets the traces, a newly mapped requirement traces to
  all artefacts of its feature and their owners are notified. An artefact may be mapped to an existing
  feature of any role (own role first).
* `FeatureEvolutionToConfig`: removed features are removed from all configurations; `feature2config`
  (ConfigCPRs) still adds new features to all configurations (not selected). Whether a configuration
  is a valid product is left to VitruvOCL.

## Scenario tests

One test per concrete instance, named after its ID (`scenario11A` = 1.1-A, ...). Each test starts
from the initial state, scripts the dialog answers by message text, performs the evolution steps up
to the inconsistency and asserts that the reactions resolved it (artefacts, correspondences,
configuration features). Dialogs that a test does not script are answered conservatively by
`answerRemainingDialogsWithDefaults()` (ignore overlaps, keep counterparts / artefacts / features,
no new feature).

Notifications need no scripted answer: `InitialStateLoader` records them (`notifications`,
`assertNotified(role, fragments...)` in `KARaceIngTestBase`), and the propagation log of the snapshots
contains them per change.

Simplifications: constraints of the scenarios (e.g. `des.TankLiftingDevice <=> ...`) are left out;
the SysML parts of 1.1-A and 4.4-A are not modelled; validity of configurations is not checked.

## Open questions

1. ELEC uses the new lightweight `electrical.ecore`. `sysML.ecore` (full SysML v2) does not fit the
   pattern: containment goes through Membership relationships and `name` is derived, so
   `EMFUtil.findContainedClasses` / `getAllNamesOfEObjects` do not work on it. Use SysML for ELEC (or
   for PRJ) anyway?
2. Removing a feature keeps its (possibly empty) group, so that the reactions know the parent feature.
   Should empty groups be removed by a reaction afterwards?
3. (resolved 2026-10-25) The pattern stopped when the parent feature corresponds to more than one
   element of the metamodel; it now uses the outermost element, see Reactions.
4. The overlap rules derive some semantics from conventions of the CAD model: a caliper with two parts
   named `*Half` is two-piece, a `Cut` boolean operation in a disc means ventilation holes, materials are
   looked up in a small table (density, specific heat, conductivity). Acceptable for the case study, or
   should these become explicit attributes (which would change the provided CAD metamodel)?
5. Generic notifications ("may have to be adapted") go to the owner of every counterpart, also for
   overlaps found by walking up the containment (e.g. a change in a caliper reaches the SIM counterpart of
   `HydraulicBrakes`). Is this the intended granularity, or should only direct overlaps notify?
6. Change order across CPSs: Vitruvius propagates a change sequence per CPS, so in one commit a removal can
   be checked (AR10) before an addition in the same commit is mapped to its feature. R6 therefore commits
   "add the integrated unit" and "remove the old devices" separately.
